What already exists for M6 to consume (nothing here gets rebuilt)

PeerNetworkService/ConnectionStrategy/DialableAddressResolver (networking), SecureSessionService/SignalIdentityVault/PreKeyBundleFactory (crypto), StorageService with dedup/receipt/transaction support (storage), HybridLogicalClock with drift guard (ordering), ChatMessageCodec/FileTransferMessageCodec (wire formats) — all proven, all staying exactly as they are. M6 is composition, not new primitives, with a few genuine exceptions below.

Something I found while re-reading that simplifies one decision a lot

I went back and checked the actual marker-byte values ChatMessageCodec and FileTransferMessageCodec use: chat is {2,3,4}, file transfer is {6,7,8} — already disjoint, both drawn from the same EnvelopeType numbering in §6, with 0,1,5,9 (HANDSHAKE_INIT/HANDSHAKE_RESPONSE/GROUP_OP/PRESENCE_PING) reserved and unused. That means "shared decrypted-message dispatch" doesn't need a new outer Envelope shell at all — a dispatcher can peek exactly one byte of the decrypted plaintext and route to the right existing codec. Much smaller piece of work than it sounded.

Decisions I need your sign-off on before I start writing anything

1	Canonical peer identity	libp2p peer ID	The checklist's own reasoning is correct — network callbacks, multiaddrs, relay/discovery, and conversation IDs already all key off it. App-identity hex ID becomes local metadata only.
2	Shared dispatch mechanism	Thin marker-byte router in node-daemon, not a new core module	Marker spaces are already disjoint (above). 3	JSON-RPC/WebSocket transport	Hand-rolled RFC 6455 WebSocket server + hand-rolled minimal JSON, pure JDK, zero new dependency	This is the one part of M6 I can actually compile and run in this sandbox, not hand-trace — real verification, matching the project's stated preference throughout the README. It's also consistent with "no protobuf yet, hand-roll wire formats" being the established convention. Trade-off: more code than pulling in a library — flag if you'd rather take a real dependency here since your machine can reach Maven Central.
4	Signal session persistence	Keep InMemorySignalProtocolStore for M6, but inject it behind a factory boundary so a JDBC-backed store is a later swap, not a rewrite	A real persistent store is a new V002 migration + a full libsignal SPI implementation — substantial scope on its own. pre-m6-checklist.md #11 explicitly says "acceptable to keep this simple, but explicit." Going through each decision

1. Canonical identity = libp2p peer ID

Best practice: Yes — standard for P2P systems (routing identity = network identity).
Difficulty: Low, but not zero — while re-checking this against the real source I found that ChatListenerMain/ChatSenderMain currently construct their SignalProtocolAddress using identity.peerId() — the app-identity hex ID, not the libp2p peer ID — while everything else (conversation-ID derivation, sender_peer_id in storage) already uses the libp2p peer ID. That's exactly the "third accidental identity convention" the README's own checklist warned about. M6's session manager has to deliberately not copy that part of M5c/M5d's pattern.
Breaks anything? No — M5c/M5d stay untouched as their own self-contained demos. M6 just won't reuse that one piece of their addressing logic. Worth flagging so it's not a surprise mid-implementation.

2. Shared dispatch = thin marker-byte router, no new module

Best practice: Yes (YAGNI, matches the project's own "promote only once a real second consumer exists" precedent).
Difficulty: Trivial — one byte peek, delegates to two already-tested codecs, doesn't touch their internals.
Breaks anything? No — purely additive new class.

3. Hand-rolled WebSocket server + hand-rolled JSON — this is the one I want to walk back partially

Splitting this in two, because they're not equally risky:

JSON parsing: low risk. It's a closed, well-understood problem, the actual shapes I need (flat-ish params objects per the §7 table) are simple, and I can write exhaustive round-trip/escaping/unicode tests and get real pass/fail signal entirely in this sandbox. I'd keep this hand-rolled.
WebSocket framing (RFC 6455): this is genuinely the one place where "absolute best practice" pulls the other way. Getting the HTTP upgrade handshake, mandatory client-frame masking, fragmentation/continuation frames, and the close handshake exactly right by hand is real, detailed protocol work — and unlike your internal binary codecs (which only ever talk to your own code), this server will eventually be hit by a real browser's native WebSocket client (M7), which is strict about spec compliance. My own round-trip tests can prove my client and my server agree — they can't prove a real browser will accept it. That's a materially weaker verification story than everything else in this project, and I don't want to undersell that to you.

So: I can build it, and I don't think it's hazardous (RFC 6455 is precisely specified, not ambiguous — I can write a real conformance-style test suite around it), but it's the one component where a mature, narrowly-scoped library (not a big framework — something like a ~50KB single-purpose WebSocket server jar) would meaningfully de-risk things, at the cost of a dependency you'd resolve on your machine, not mine. I'd like your explicit call here rather than deciding it myself, since it's a real trade-off, not a clear win either way.

4. Keep sessions in-memory, inject the store via a factory seam

Best practice: Honestly, no — for a real product, persistent sessions are the correct end state (restart currently forces every peer to re-handshake, and repeatedly reusing the same one-time prekeys across sessions is itself a Signal Protocol hygiene problem).
Difficulty: This is the one I'd call genuinely close to "hazardous" if we tried to do it inside M6. A real fix means a new V002 migration plus a full JDBC-backed implementation of libsignal's SignalProtocolStore (six sub-interfaces: identity/prekey/signed-prekey/Kyber-prekey/session/sender-key stores), correctly serializing SessionRecord's internal chain-key state — comparable in scope to M2a+M2c combined, on its own.
Breaks anything? No either way — deferring it changes nothing about existing code, and building it now would be purely additive too.
My recommendation stands, but I want to be honest that "keep it simple" here is a real scope trade-off, not a free lunch — I'm deliberately not solving a real gap, with a seam left so it's a later swap, not a rewrite.

5. Signed discovery records

Best practice: Unambiguous — unsigned bundle-bearing records are a real MITM vector the moment they exist, exactly as §15 already warns.
Difficulty: Moderate, and worth spelling out why: this needs a self-certifying design — the record has to carry the publisher's raw Ed25519 public key so a verifier who has never talked to them before can (a) recompute the SHA-256 hex peer ID from it and confirm it matches what they looked up, then (b) verify the signature with that same key. This connects back cleanly to M1.5's own finding — since the libp2p peer ID and the hex ID are two encodings of the same Ed25519 key, one signature authenticates both simultaneously. Real design work, a few hours, not hazardous.
Breaks anything? No — new record version, relay-server stays payload-agnostic (already true today), zero changes to the discovery wire protocol itself.

6 & 7 (transaction boundaries, error vocabulary): Both low-risk, mechanical, additive. No real concerns.

Something I want to flag that wasn't on the original list at all

Re-checking libsignal's SignalProtocolStore usage pattern for M6 specifically (holding many simultaneous peer sessions, which no prior milestone did): the reference InMemorySignalProtocolStore isn't documented as thread-safe. Today, every demo Main only ever has one session active at a time, so this never mattered. M6's whole point is concurrent sessions from multiple peers, handled on Netty's I/O threads. Without a synchronization wrapper around the store, two peers messaging at the same moment could race on the same underlying map. This isn't hazardous to fix — a single synchronized wrapper class around the store calls — but it's a real correctness issue that only exists because of what M6 is, and nothing in the existing docs called it out. Good thing to catch now rather than mid-build.
